# 1. Перечень автоматизируемых сценариев
   ## 1.1. UI-тесты (форма «Обычная оплата»)
   **Позитивные сценарии:**

1) Успешная оплата тура с валидными данными и картой APPROVED (1111 2222 3333 4444) → появляется сообщение об успехе, в БД сохраняется запись со статусом успеха и способом оплаты.

2) Успешная оплата с граничными значениями срока действия карты (текущий месяц/год) → операция проходит, данные сохраняются.

   **Негативные сценарии:**

1) Оплата картой DECLINED (5555 6666 7777 8888) → сообщение об отказе, в БД фиксируется отказ.

2) Отправка формы с пустым полем «Номер карты» → ошибка валидации, запрос в банк не уходит.

3) Ввод номера карты с буквами или неверной длины → ошибка валидации.

4) Пустые поля «Месяц» / «Год» → ошибка.

5) Указан прошедший год → ошибка.

6) Месяц вне диапазона 01–12 → ошибка.

7) Пустое поле «Владелец» → ошибка.

8) Пустое поле CVC или CVC из 2/4 цифр → ошибка.

9) Полностью пустая форма → ошибки по всем полям одновременно.

   ## 1.2. Проверки в БД
**После успешного платежа:** наличие записи с корректным статусом и способом оплаты (DEBIT).

**После отказа:** запись со статусом DECLINED.

Отсутствие данных карты в любой таблице БД.

   ## 1.3. API-тесты (опционально)
Проверка запроса, отправляемого браузером после заполнения формы: код ответа, тело ответа, статус операции.

# 2. Перечень используемых инструментов с обоснованием
   **Java 11**	Язык автотестов.	Совместимость с Selenide, JUnit *требование курса*

   **JDBC + HikariCP**	Проверки в БД	*Прямые SQL-запросы, пул соединений для стабильности*

   **Allure**	Отчётность	*Наглядные отчёты, шаги, скриншоты, интеграция с Gradle*

   **Git / GitHub**	Версионирование, Issues	*Удобство совместной работы*


# 3. Перечень и описание возможных рисков при автоматизации

   **Нестабильность симулятора банковских сервисов** — общий сервис для всех студентов, возможны задержки или временная недоступность. Митигация: ретраи, проверка логов по IP, связь с наставником.

   **Сложность настройки подключения к СУБД** — неверный URL/пароль в application.properties приведёт к падению всех тестов. Митигация: проверка через docker exec и SHOW DATABASES до запуска тестов.

   **Плавающие UI-тесты из-за таймингов** — Selenide снижает риск, но полностью не исключает. Митигация: стабильные селекторы, явные ожидания.

   **Нехватка времени на опциональные пункты (API, две БД)** — приоритет обязательным требованиям. Митигация: фиксация scope в плане и своевременное информирование наставника.

   **Изменение IP-адреса провайдером** — логи перестанут фильтроваться. Митигация: перепроверка IP перед анализом логов.
